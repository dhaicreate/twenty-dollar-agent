Claude Code routine not running, or not doing what you expected?

Find your symptom below. Each one has the likely cause and a check you can run in a couple of minutes.

  1. It never ran (no new session at all)
  2. It shows as run, but nothing changed
  3. It pushed to a claude/… branch, not main
  4. Push rejected (non-fast-forward / detached HEAD)
  5. 403 or host_not_allowed on a network request
  6. My MCP server or local files aren't there
  7. It worked for a few days, then stopped
  8. It runs, but repeats work or forgets what it did
  9. Still stuck: the 2-run canary test

1. It never ran

Likely causes

  • Wrong kind of schedule. Cloud routines run on Anthropic's servers with your laptop off. Desktop scheduled tasks need the app open and the machine awake. /loop only lives inside an open session. Check which one you created.
  • Routine disabled, or a one-off that already fired. Open claude.ai/code/routines or run /schedule list and check it's enabled and shows a next run time.
  • Timezone. Times are shown in your local timezone. A 6:00 run may be 6:00 somewhere you didn't expect. Runs can also start a few minutes late.
  • Usage limit. If your plan's usage window is used up, scheduled runs are rejected until it resets. Recreating the routine won't help.
  • Org policy. On Team and Enterprise plans an owner can turn routines off.

Check

Press Run now (or /schedule run). If a manual run works but the schedule doesn't fire, the problem is the trigger, timezone or usage, not your prompt.

2. It shows as run, but nothing changed

A finished run only means the session started and exited without an infrastructure error. It says nothing about whether your task worked. The usual reasons:

  • It committed but never pushed. The cloud machine is thrown away after the run, so anything not pushed is gone. Make the push an explicit last step in your prompt, and tell it to report the commit hash.
  • It pushed somewhere else. See #3.
  • It hit a blocker and stopped politely. Open the run's transcript and read the end of it. Agents often say "I couldn't do X" in a place nobody reads.
  • It waited for an answer. Nobody is there during a scheduled run. Prompts that say "ask me if unsure" stall. Tell it what to do when unsure (write it down and carry on).

Check

Make the routine finish by printing a short receipt: branch, commit hash, pushed yes/no, files changed. If the receipt is missing, the run ended early.

3. It pushed to a claude/… branch, not main

By default the agent works on a branch prefixed claude/ unless your prompt names a branch. If you want main (for example, GitHub Pages serving from main), say it in the routine prompt in plain words: "commit to main and push to origin main". If main is protected by a branch rule on GitHub, the push will fail and you need either a PR flow or to change that rule.

4. Push rejected: non-fast-forward or detached HEAD

This one bit the $20 Agent on its third run. The routine's checkout was a detached HEAD with an older local main. The agent committed, ran git push origin main, and git pushed the stale local branch, which GitHub rejected.

Check and fix

git branch --show-current   # empty output = detached HEAD
git push origin HEAD:main    # push the commit you're actually on

If something else also pushed to main during the run, git pull --rebase origin main first, then push again. Put both lines in your rulebook so the agent doesn't rediscover this every run.

5. 403 or host_not_allowed on a network request

The routine's environment controls which sites it can reach. The default allows package registries and common developer sites, not your API or random websites. A 403 mentioning host_not_allowed is the network policy, not the website. Add just the domain you need in the environment settings, rather than opening everything.

Related trap: code that works from the agent's machine may not work in a visitor's browser. The $20 Agent's payment page called the public Solana RPC, which answers server requests but refuses browser requests with 403. Test anything customer-facing in a real browser.

6. My MCP server or local files aren't there

The cloud run starts from a fresh clone of your repo on a fresh machine. MCP servers added locally with claude mcp add, files outside the repo, and your shell's environment variables don't come along. Use account connectors, a reviewed .mcp.json in the repo, or the environment's variables and setup script.

The reverse is a problem too: every connector on your account is attached by default. If you've connected email, calendar or drive, an unattended agent gets them unless you remove them in the routine's connector step. Remove anything the job doesn't need.

7. It worked for a few days, then stopped

  • GitHub connection expired. Runs get skipped, and after a while the routine can switch itself off. Reconnect GitHub and check the routine is still enabled.
  • Usage. A long or chatty run every hour uses up plan usage faster than you'd expect. Lower the frequency or make each run do less.
  • The repo grew a conflict. If you edit the same files by hand, the agent's push can start failing every run. Keep your own edits out of the agent's working files, or have it rebase first.

8. It runs, but repeats work or forgets what it did

Every run starts with no memory. The only memory is what it wrote to the repo last time and pushed. Give it:

  • a rulebook (AGENT.md) it reads first, with the steps for each run;
  • a state file it updates (cycle number, last run, current plan);
  • a dated journal entry per run, and a rule to read the last few before deciding anything.

The free AGENT.md generator writes this structure for you.

9. Still stuck: the 2-run canary test

  1. Temporarily replace the routine prompt with something harmless that proves the basics, for example: 
    Run: git branch --show-current; git rev-parse HEAD; date -u.
Append the output to canary.txt, commit, and push to origin HEAD:main.
Then print: BRANCH, COMMIT, PUSHED (yes/no), UTC time.
  2. Press Run now. If canary.txt doesn't appear on GitHub, the problem is repo access, branch rules or pushing. Fix that first.
  3. Leave it on schedule for one interval. If the manual run worked and the scheduled one didn't appear, it's the trigger, timezone or usage.
  4. Put your real prompt back, keeping the receipt at the end.
